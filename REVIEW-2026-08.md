# Dr Evide — engineering + design review

Reviewed: 6 Aug 2026 · commit at `apps/`, `packages/` as of this date.

## Verdict first

The core is strong. `packages/core` as the single source of truth, TrustScore as a pure
function of `(doctor, context)`, golden score tests, the local-first emergency check, and
`check:integrity` as a CI gate are all better than the median production repo. Nothing below
asks you to change the scoring model or the taxonomy.

What's missing is the ring around that core: the app has no error paths, no security headers,
no observability, health data ends up in URLs, and the interface fails contrast for exactly the
users it was built for. Three of the findings are launch blockers.

Findings are ordered by consequence, not by effort.

---

## P0 — blocks launch

### 1. Health data leaks into URLs, logs, and third-party referrers

`packages/core` is careful: symptom text is classified in memory, never persisted, never
logged, `no-store` on the response. Then the derived condition keywords go straight into a
query string:

```
/results?specialty=cardiology&conditions=chest+pain
/doctor/12?specialty=cardiology&conditions=chest+pain&lat=…&lng=…
```

That URL lands in:

- **Browser history** — on a shared phone, which is normal in the launch area.
- **Server access logs** — every reverse proxy and CDN logs the full path by default.
- **The `Referer` header sent to third parties.** `/results` renders Leaflet, which fires ~20
  tile requests to `tile.openstreetmap.org` per view. Each one currently carries
  `Referer: https://drevide…/results?conditions=chest+pain`. The same applies to the
  "Get directions" link out to Google Maps from `/doctor/[id]`.

Under the DPDP Act 2023 these keywords are sensitive personal data derived from a health
complaint, attached to an IP. The code comments show the team knows this; the URL is the hole.

**Fix:** `Referrer-Policy: no-referrer` globally (stops the third-party leak immediately, one
line), then move `conditions` out of the URL — `sessionStorage` on the client, or an opaque
short-lived search token. `lat`/`lng` should go too; precise geolocation in a URL is its own
problem.

### 2. No security headers at all

`next.config.mjs` has no `headers()` block. Missing: `Content-Security-Policy`,
`Referrer-Policy`, `X-Content-Type-Options`, `X-Frame-Options` / `frame-ancestors`,
`Strict-Transport-Security`, and `Permissions-Policy`. The last one matters specifically here —
the app requests geolocation, and nothing currently denies camera, microphone, and payment to
embedded content.

### 3. A network failure is indistinguishable from "no doctors found"

`apps/web/src/app/results/page.tsx`:

```ts
try {
  const res = await fetch(`/api/doctors?${params}`);
  const json = await res.json();
  if (current) setData(json);
} finally {
  if (current) setLoading(false);
}
```

No `catch`. On a dropped connection — the normal condition on rural Kerala mobile data — the
promise rejects, `data` stays `null`, and the page renders:

> No Dermatology doctors within 5 km. Try widening the radius.

The user is told there are no doctors near them when the truth is the request never landed.
For a product whose job is getting an unwell person to a doctor, a false negative is the worst
possible failure mode. It also leaves an unhandled rejection on every failed search.

**Fix:** add a `catch`, add an explicit `error` state, render a retry affordance. Also handle
`!res.ok` — a 500 currently sets `data` to `{error: …}` and renders the same empty state.

### 4. Text contrast fails WCAG AA

`--text-faint: #938F84` on `--bg: #FAFAF8` measures **3.1:1**. AA requires 4.5:1 for body text.
It is used for:

- the "Malayalam & English both work" hint under the main input
- the entire site footer — **including the medical disclaimer and the `108` emergency number**
- `.cred-row__note` (the "not yet verified" explanation, i.e. the honesty signal)
- specialty sub-labels, the "of 100" on the TrustScore ring, "clinic consult"

`--warning: #D98A0B` at a 12% tint measures **2.7:1** — that's the "Sample data" pill, which is
the legal marker saying these people aren't real.

The target user is often older, often outdoors in bright sun, often on a cheap screen. This is
the highest-impact UI fix in the list and it's a token change, not a redesign.

**Fix:** darken `--text-faint` to roughly `#6E6A60` (the ramp already has it, ~5.5:1), and use
a darker warning for text-on-tint.

## P1 — engineering hardening

### 5. Radius constants exist in three places and disagree

| Where | MIN | DEFAULT | MAX |
|---|---|---|---|
| `packages/core/src/geo.ts` | 1 | **15** | 100 |
| `apps/web/.../RadiusControl.tsx` | 1 | **5** | 25 |
| `apps/mobile/app/results.tsx` + `src/lib/api.ts` | 1 | **5** | 25 |

The web slider opens at 5 km while `doctorSearchSchema` defaults to 15 km and the README
documents 15. A bare `/api/doctors` call and the same search through the UI return different
result sets. This is precisely the duplication the README forbids ("if both apps need it, it
belongs in `packages/core`") — it just happens to be numbers rather than a module.

### 6. `LIMIT 200` truncates before ranking

```sql
ORDER BY distance_km
LIMIT 200
```

The rows are cut by **distance**, then ranked by **TrustScore**. Once a specialty has more than
200 doctors in a radius, the highest-scoring doctor can be silently dropped for being 12 km
away instead of 11. That directly contradicts "distance is a filter and a tiebreaker, not a
quality signal." Latent at current data volume; a correctness bug the day real data lands.

### 7. The mobile app never asks where you are

`apps/mobile/app/results.tsx` passes `...DEFAULT_LOCATION` — Edappal town centre, hardcoded.
The product is "find the right doctor **near you**"; on the phone, where that phrase matters
most, it means "near the town centre." It also corrupts scoring: the `nearness` term inside
`accessibility` (10% of TrustScore) is computed against the wrong origin, so the app and the
website will show different scores for the same doctor. The repo's central promise is that
they don't.

### 8. Zero observability

There is no logging, no request ID, no health endpoint, no counters. The LLM path is a
deliberate silent-fallback:

```ts
} catch {
  return null;   // timeout, 429, network, bad JSON — all the same
}
```

Swallowing the *content* is correct (the body is the user's symptom text). Swallowing the
*fact* is not. If the API key expires, every user quietly drops to keyword routing and nothing
anywhere says so. Emit a counter — `llm_routing_fallback{reason}` — with no payload.

Same for the rate limiter: a 429 storm should be visible.

### 9. No error, loading, or not-found boundaries

No `error.tsx`, `global-error.tsx`, `not-found.tsx`, or `loading.tsx` anywhere in the App
Router. `getDoctor()` throwing (DB down, statement timeout — both explicitly configured to
happen after 5s) renders the raw Next error page.

### 10. No tests outside `packages/core`

109 tests, all on the pure core. Nothing covers the API routes, the HTTP-level zod boundaries,
the rate limiter's window behaviour, or the LLM fallback chain. The riskiest code — the
untrusted-model parser and the emergency backstop in `llm-routing.ts` — has no test.

### 11. Smaller items

- **`pg` Pool leaks on hot reload** — needs a `globalThis` singleton in dev, or every save
  opens 10 more connections.
- **Rate-limit key is spoofable** — `x-forwarded-for` is taken from the client; only trust it
  if the platform overwrites it, and say which hop you trust.
- **`/api/doctors` is unmetered** — public, unauthenticated, DB-backed, no cache headers.
- **`parseFloat(lat) || DEFAULT`** in `doctor/[id]/page.tsx` treats a legitimate `0` as
  missing. Harmless in Kerala, wrong in principle.

## P2 — UI / UX

### 12. The interface is English-only while the product promises Malayalam

The home screen says "Malayalam & English both work" and the taxonomy carries full Malayalam
and Manglish keyword sets — real, careful work. Then someone types `മുടി കൊഴിച്ചിൽ` and gets
back an entirely English results page: "Dermatology near you", "TrustScore", "NMC verified",
"Within 5 km". The input is bilingual; the output isn't.

This is the largest UX gap in the product. Even a partial pass — headings, the TrustScore
explainer, the emergency copy, and the disclaimer — changes who can use it.

### 13. TrustScore is a number with no anchor

A card shows `82`. Is that good? There's no scale, no distribution, no comparison. The ring
conveys proportion-of-100, but 100 isn't achievable in practice, so the top doctor in a list
can look mediocre. Add a qualitative band ("Strong credentials"), or show where the score sits
against the others in the same result set.

### 14. No page-level sample-data warning on the web

Every doctor is fictional. The results page returns `sample_data: true` from the API — and
never renders it. The only signal is a 24px, 2.7:1-contrast pill per card. This should be a
persistent banner until real NMC-verified data replaces the seed; it's the clearest legal
exposure in the product and currently the quietest thing on the page.

### 15. The emergency alert can sit below the fold

On mobile web, the alert renders under a 3-row textarea, a hint row, and a 58px button. After
submitting, the most important message in the product may be off-screen and the page doesn't
scroll to it. It also has `role="alert"` but focus never moves — a screen reader user stays on
the submit button.

### 16. Loading and empty states dead-end

- Loading is the bare string "Finding doctors…" with no skeleton, so the layout jumps and the
  wait feels longer than it is.
- Stale results stay on screen when the specialty changes — old name, old list.
- The empty state offers "try widening the radius" but not the widening. Better: compute the
  radius that *would* return results and offer it as a button, or show the nearest three
  regardless of radius, clearly marked as further away.

### 17. Accessibility, remaining

- No skip-to-content link.
- The primary input has only an `aria-label`; placeholder-as-label disappears on focus.
- `.pill` is 24px tall and `.link-back` has no padding — both under the 44px touch target
  minimum.
- The design system ships a full dark theme that the app never uses (`[data-theme="dark"]` in
  `colors.css`). A health app read in bed at 2am is the use case.

## P3 — reach

### 18. The product is invisible to search

No `robots.txt`, no `sitemap.ts`, no `generateMetadata` on doctor profiles, no JSON-LD.
Every doctor page shares one title ("Dr Evide — find the right doctor near you"). A
doctor-discovery product lives on "dermatologist near Edappal" queries; right now none of the
20 profile pages can rank for anything. `Physician` / `MedicalBusiness` structured data is the
single highest-leverage addition once real data lands.

### 19. The PWA doesn't install

`manifest.json` has `"icons": []`, so no install prompt on Android — the dominant platform in
the launch area, where an installable app avoids a 30MB store download. `background_color`
(`#fafaf9`) also doesn't match the token (`#FAFAF8`).

### 20. No OG image or Twitter card

Every share of a doctor profile renders as a bare grey link.

---

## Suggested order

1. Contrast tokens, `Referrer-Policy`, results-page error state — hours, and they're the three
   that can actually hurt someone.
2. Security headers, error boundaries, radius constants into core, mobile geolocation.
3. Sample-data banner, TrustScore anchoring, skeletons, empty-state recovery.
4. Malayalam UI pass, SEO + structured data, PWA icons.

Steps 1 and 2 should land before any real doctor's name appears in the database.
